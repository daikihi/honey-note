## 2. 現状の構造と重要な差分

### 2.1 現在のデータ経路

```text
一覧: front → GET /honey-note/api/honeys
            → get_all_honies → repository::honeys → SQLx Honey → Vec<models::honey::Honey>

詳細: front → GET /honey-note/api/honey/{id}
            → get_honey_by_id → repository::honeys → HoneyDetail

登録・編集: HTML + front/edit_mode
            → HoneyNewRequest / HoneyEditRequest
            → Controller → UseCase → HoneyDetail → repository::honeys → honey + honey_flower

バッチ: JSONL → JsonHoney → models::honey::Honey
            → insert_honey_if_not_exists → SQLx Honey → honey
```

`Honey`と`HoneyDetail`という異なる形が一覧・バッチと詳細・更新で使われている。新モデルへの切り替えでは両方を追う必要がある。

### 2.2 今回の変更に直結する現状

| 確認事項 | 根拠 | 変更への影響 |

## 4. common：RepositoryとDBアクセス

### 必須の変更箇所

- `common/src/repository/honeys.rs`
  - 現在の6操作（登録・更新・重複判定・ID存在確認・一覧・詳細）を新しい責務に対応させる。
  - 商品登録と既存商品へのボトル追加を分け、同一商品を複数本所有できるようにする。
  - ボトル・観察・メモ・産地の保存／取得を追加する。
  - 商品更新、ボトル更新、観察操作、メモ更新のトランザクション境界を整理する。
  - 現在の`honey.user_id`絞り込みを、新しい非公開方針とBottleのownerに合わせる。子レコードのIDだけではアクセスを許可しない。
  - `create_model_honeys`等の一覧用変換、バッチ用`insert_honey_if_not_exists`、モック実装を更新する。
- `common/src/infrastructure/db/sqlx/honey.rs`
  - DB行型とINSERT・UPDATE・SELECT・重複判定SQL、共通モデルへの変換、同ファイル内のテストDDLを更新する。
  - ボトル・観察・メモ・複数産地のSQL実装を追加する。別モジュールにするかは設計時に決定する。
- `common/src/repository.rs`、`common/src/infrastructure/db/sqlx.rs`
  - 追加Repository／SQLxモジュールの登録。

### 関連して確認する箇所

- `common/src/repository/honey_repository.rs`は実動経路とは別の、登録のみを持つ同名traitとモック。現在のController・UseCaseは`repository::honeys`を参照しており、この別traitの利用箇所は見つからない。移行後の削除・統合候補。
- `repository::honeys::get_all_honies`とSQLxの全件取得はユーザーで絞らない旧経路。現行APIはユーザー引数付きtrait経路を使う。未使用経路を新設処理から誤って使わないよう整理候補にする。
- 蜜源名のID解決SQLにはuser_id条件がない（`honeys.rs:83,99`）。養蜂家・蜜源をID参照に変える際、他ユーザーのレコードとの関連付けを防げることを確認する。
- `common/src/repository/beekeepers.rs`、`flowers.rs`と各SQLx実装は、関連ID解決・所有権確認やID型の変更を行う場合に波及する。都道府県は養蜂家住所にも使うため、蜂蜜産地の変更だけを理由にマスターごと削除しない。

## 5. DB：保存構造と移行

既存の対象DDL:

- `resources/db/migrations/0004_2025-08-09_1500_create_honey_up.sql`
- `resources/db/migrations/0005_2026-03-19_1010_create_users_up.sql`

ローカルDBでもhoney・honey_flower・honey_batch_infoを確認し、honey_bottle・honey_observation・bottle_memoは存在しなかった。

| 現在 | 必要な変更 |
| --- | --- |
| honey | 静的商品情報の保存先にする。種類・作成更新日時など新モデルとの不足を埋める。所有・可視範囲の具体的な表現は別途決定 |
| honey内のharvest_year / purchase_date | ボトル側へ移す |
| honey内の単一origin_country / origin_region | 複数国・複数地域を保存できる構造へ変更 |
| honey内のnote | 新しいBottleMemoとの対応を決める。自動移行先は未確定 |
| honey_flower | 商品と蜜源の関連として継続候補。商品IDと蜜源ID、整合性・更新処理を新モデルに合わせる |
| honey_batch_info | Honey直下からBottle直下の観察に再編。既存の色・味・状態・水分量の変換先を決める |
| ボトルの保存先なし | 商品ID、owner、採蜜年、日付、初期量・残量g、ロット番号、作成更新日時の保存構造を追加 |
| ボトルメモの保存先なし | 独立ID、bottle_id、text、作成更新日時。ボトルごと最大1件を保証 |
| 構造化された観察の保存先が不足 | 観察ID・秒までの観察日時と色／香り／味／苦味・えぐみ／結晶化／水分量／好み／メモを保存 |

検討するDB制約は外部キー、ボトルごとのメモの一意性、1〜10の尺度、gの値域、所有者・商品・観察検索用インデックス。量の小数精度、残量と初期量の関係、削除時の扱いは未確定であり、この調査では制約値を決めない。

Aroma/Taste/CrystallizationをRustで分けることと、DBで別テーブルにすることは別判断。新規DDLファイルを追加するか開発用DBを再構築するかも、データ保持方針と合わせて決める。BC許容を理由に既存DBやバックアップを削除しない。

現行Controllerテストには401を成功条件に含めるものがあり、認証済みの保存成功を十分には検証しない。移行後は認証済み操作が成功することと別ユーザーが読めない／更新できないことを別々に確認する。

### 必要な検証シナリオ

1. 同じ商品を3本登録して、それぞれの量・日付・メモ・観察が独立する。
2. 同名・同養蜂家でも産地が違えば別商品として登録できる。
3. 複数国・複数地域、産地不明、国のみを保存して復元できる。
4. 1本に同日でも複数観察を記録し、秒までの日時・10段階評価・苦味/えぐみ・メモが再表示される。
5. ボトルメモは最大1件で更新でき、観察メモにも同じ内容を書ける。
6. 商品・ボトル・観察・メモのIDを指定しても別ユーザーのデータを取得・変更できない。
7. 評価1/10を受け入れ、0/11を拒否する。未評価は別扱いにする。
8. 日付が時差でずれず、gの数値が往復で維持される。量の境界値は不変条件の合意後に定義する。
9. ボトルだけの更新で商品・養蜂家・蜜源・観察が意図せず変わらない。
10. JSONLの再実行と複数本登録を区別し、途中失敗時に不完全な関連を残さない。

### 配信と運用

- `.github/workflows/ci.yml`にはworkspaceテストとWASMテストがある。モデル変更後は両方を通す。
- HTMLは`/honey_note/javascript/front.js`を参照し、READMEにはwasm-packから`server/src/assets/javascript/`へ出力する手順がある。型変更に合わせてWASM/JSを再生成・同時配信する。生成物を手で直す作業ではない。
- `specs_dev/2026-05-20-p1-st1/operator_specification.md`のバックアップ対象・参照ID・復旧順序、および`2026-06-19-p1-s2-backup-storage-format/`の形式検討にも新Entityが影響する。今回のソース一覧では専用restore/verifyバッチは確認できず、既存実装変更と将来仕様への追従を区別する。
- 新しい入出力とDBが確定した後に現行仕様書や運用手順を更新する。今回、他テーマの仕様やREADMEへの転記はしていない。

## 10. 変更順序の検討材料

以下は依存関係から整理した順序であり、実装開始や最終設計の承認を意味しない。

1. 残る仕様を確定する：一覧の単位、分類型、商品識別、非公開の表現、旧データ・既存項目の扱い。
2. common-typeへ新しいモデルと入出力を定義する。最初は旧型と併存させ、既存呼び出しを壊さない。
3. DB保存構造とcommonの新しいRepository／SQLを対応させ、保存・取得の往復を検証する。
4. serverの新しいUseCase／APIを接続し、認証・所有者の確認を検証する。
5. batchsの投入経路を接続し、登録単位と再実行を検証する。
6. frontとHTMLを新しいAPIへ切り替え、実データの再表示まで確認する。
7. データ保持方針に従って移行または再構築し、旧型・旧経路を除去する。WASMとserverを整合した状態で配信する。

コンパイル上の併存は段階的作業のためであり、旧APIの後方互換を恒久的に維持する要求ではない。

## 11. 実装設計前に残る判断

| 論点 | なぜ必要か |
| --- | --- |
| 一覧は商品中心かボトル中心か | 現行一覧の購入日・詳細IDと新モデルが一致しなくなるため |
| 同じ商品の判定・選択方法 | 名前だけの判定を置き換え、同名産地違い・同商品の追加購入を扱うため |
| 分類型の表現 | 既存は文字列型と固定選択肢。メモへの自由記述許可だけでは専用項目の型は確定しないため |
| 英語名・用途・タグの存続と所属 | 既存モデル／画面にはあるが新モデル案に対応先がないため |
| 旧観察のstate/taste/note、honey.noteの扱い | 新しい観察・Taste・2種類のメモに単純な一対一対応がないため |
| Honeyのユーザーへの所属・権限 | 当面非公開とBottle.ownerは確定しているが、商品そのもののアクセス条件が未確定のため |
| データを移すか再投入するか | BC許容だけでは既存レコードの削除・変換方針が決まらないため |
| 量・採蜜年・水分量・日付等の不変条件 | g・日付・10段階以外の値域、必須項目、空値の扱いが未確定のため |
| 観察日時の衝突・修正・削除の操作 | 秒までの日時で複数観察を記録する。同一秒も別IDで保存し、不要な観察はdeleted_atによって論理削除する |
| バッチで1行を何として扱うか | 商品だけか所有ボトル込みか、再実行用の識別子が必要なため |

今回の成果物は変更箇所の洗い出しであり、これらを推測で埋めた実装やDB変更は行っていない。

## 12. 調査後の回答による更新

前節までの未決事項は調査時点の記録として保持する。最新の回答は[方針確認記録](方針確認記録.md)の「変更箇所調査への回答」に記録した。

- 一覧はボトル単位とし、名前・産地・購入年・ボトルIDを表示上の識別材料とする。同日同商品の複数本を許容する。
- 英語名・用途・タグを残す。英語名をHoney、用途・タグをBottleへ置く案を説明中。
- 旧データの移行は不要となり、破棄して再投入する方針。移行用コードより新規DB構築と再投入手順が対象となる。
- 所属ユーザーのみ書き込み、現段階では他人のボトルは読み取り不可とする。
- 量・採蜜年はNULL／未入力を許容し、後から更新する。
- 観察は秒までの日時を持ち、同日でも複数回記録する。DB・Repository・API・画面・テストをこの粒度へ揃える。同一ボトル・同一秒でも別IDで保存する。日時に一意制約は設けず、不要な記録は論理削除する。
- 同一商品の判定にBottleIdを流用せず、個体の識別とHoneyIdによる商品への所属を分ける旨を説明する。

### 評価UIの追加方針による影響

- Mouthfeel・Finish・CrystalTextureも文字列分類から10段階の数値へ変更対象となる。香りの強さ等と合わせて、共通型・DTO・SQL・スライダー・再表示・検証を揃える。
- 香りの種類はenum相当の分類とする。複数選択を採用する場合はモデル・JSON・DBも複数値を扱う必要があるが、複数選択＋その他の自由記述は承認済み。
- HTMLの評価入力を1〜10・整数刻みのスライダーへ変更し、現在値・両端の説明を表示する。未評価の保存方法は別途設計する。
- 蜜源植物の登録数からHoneyTypeを決める場合、商品作成・更新・蜜源変更・バッチ投入・取得表示の判定を統一する。入力途中と蜜源特定済みの区別、および自動判定の確定仕様は未決定。

### 既存マスターデータ投入の登録単位の確定

- `batchs/src/honey_loader/honey_loader_usecase.rs`は、1入力行について商品情報の登録・参照解決とボトル1本の登録を行う変更対象とする。
- 同名商品の複数行を失わないよう、現在の名前＋user_idによる重複排除をボトルの重複判定には使わない。
- `honey_loader_models.rs`の既存idを個体識別に使えるか確認し、同一商品の複数本と同一データの再実行を区別する。商品IDとの対応方法は未確定。
- テストでは、同一商品に相当する異なる入力レコード2行から2本を登録できることを確認する。同じ入力の再実行については識別・更新方針の確定後に検証する。
- 今回の回答により、第7節・第11節で未決としていた「商品だけ投入するかボトルも作るか」は、現在の蜂蜜マスターデータバッチについて解決した。

### 蜜源登録数による種類判定の確定

- HoneyTypeは登録された蜜源植物が1〜2種類なら単花蜜、それ以外は百花蜜とする。入力途中・特定済みを区別する追加状態は設けない。
- 商品登録・蜜源更新・バッチ投入・取得表示でこの規則を統一する。判定を都度計算するか保存するかは実装設計で整理する。
- 判定テストには0・1・2・3種類と、追加・削除で境界をまたぐケースを含める。


### 検索UX・最小入力・ログ再生の追加影響

- 蜂蜜名・養蜂場名・購入年で候補を取得する検索API／UseCase／Repository／SQLとfrontの検索ボックス・候補選択・新規登録導線を追加する。購入年はボトル側から検索し、同じ商品の複数候補の表示を整理する。
- 商品名だけの登録・後日の編集を許容するようHTMLのrequired、DTO検証、DBのNULL許容を揃える。将来のフォーク機能は今回の必須実装に含めない。
- 同日で時刻の異なる2観察が両方保存・表示されること、日時編集、タイムゾーンの往復をテスト対象にする。同一秒の2件も別IDで保持し、一方だけ論理削除して通常の取得から除外できることを検証する。
- 香りは複数選択とその他の自由記述をモデル・JSON・DB・入力・表示へ反映する。
- 復旧工程はマスター投入と過去ログの全順序再生を合わせて設計する。現行PutLogは処理前の入力ログなので、成功操作・ユーザー・払い出しID・操作順が復元可能か調査する。順序だけで冪等性を保証済みとはしない。


### 観察の論理削除による追加影響

- common-typeのHoneyObservation、DBの観察行に任意のdeleted_atを追加する。Bottleと観察日時の組に一意制約を設けない。
- commonの通常取得はdeleted_at未設定で絞り込み、ID指定の論理削除処理を追加する。
- serverに所有者を確認した観察削除の操作を設け、frontから個別の観察を削除できるようにする。
- ログ再生・バックアップで削除状態と削除日時を維持する。
- 同一秒の2件を保存、一方を論理削除、他方が残ること、削除行が物理的には存在すること、他ユーザーが削除できないこと、復旧後も削除状態が維持されることを検証する。
