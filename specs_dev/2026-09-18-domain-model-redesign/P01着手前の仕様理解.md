## 目的とモデルの境界

商品と所有する1本を区別し、同商品の複数本と、各ボトルの複数観察を独立して保存・表示できるようにする。

| 概念 | 理解した責務・関係 |
| --- | --- |
| Honey | 商品名・養蜂家・蜜源・産地などの商品情報。産地が異なれば別商品。1商品に複数ボトルが所属 |
| HoneyOrigin / OriginArea | 商品の複数国・複数地域。地域は自由記述。産地不明は空リスト、国のみ既知なら地域を空にできる |
| HoneyBottle | 所有する物理的な1本。商品参照・所有者・採蜜年・購入日・初期量・残量・ロット番号・開封日・消費完了日を持つ |
| HoneyObservation | ボトルの時点ごとの観察。色・香り・味・結晶化・水分量・好み・観察メモ。独立したIDと秒までの観察日時を持つ |
| Aroma / Taste / Crystallization | 観察項目を意味でまとめるValue Object。DBのテーブル分割とは別判断 |
| BottleMemo | ボトルごと最大1件の更新可能な独立Entity。観察メモとの内容の重複を禁止しない |

Entity別ID、新規作成入力と永続化済みEntityの分離を計画している。詳細取得の合成モデルはEntityとは区別する。英語名・用途・タグは存続が確定しているが、英語名をHoney、用途・タグをBottleに置く記述は配置案として扱う。

## 入力・出力・振る舞い

- 一覧はボトル単位。名前・産地・購入年・ボトルIDが識別の手掛かりとなり、同日同商品の複数本も別個体として扱う。
- 追加先商品は蜂蜜名・養蜂場名・購入年などによるサーバー検索結果から選択する。候補がなければ新規登録する。購入年はBottleの購入日から検索する情報であり、Honeyの属性ではない。
- 商品名だけで商品と最初の1本を登録でき、後から補完できる。量・採蜜年は任意。IDや所有者などのシステム側情報まで省略可能という意味ではない。
- 購入・開封・消費完了は日付、観察は秒までの日時。作成更新日時とは区別する。
- 同じボトル・同じ秒の観察を許容し、ObservationIdで識別する。削除時はdeleted_atを設定し、通常の一覧・詳細から除外する。自動重複削除は行わない。
- 評価は1〜10の整数スライダー。苦味・えぐみは1項目。口当たり・余韻・結晶の質感も数値化する。両端や中立点の詳細は未確定。
- 香りは花・果実・ハーブ・木・スパイス・カラメル・発酵の複数選択と、その他の自由記述。メモはプレーンテキストで用途を制限しない。
- 蜜源植物の登録種類数が1〜2なら単花蜜、0または3以上なら百花蜜。入力途中・特定済みという追加状態は設けない。
- 所属ユーザーが読み書きし、現段階で他ユーザーへの共有は行わない。Honeyの具体的な所属表現とBottle.ownerとの整合は詳細化が必要。
- 量の単位はg。値域、小数精度、初期量と残量の関係は未確定。

## 全体計画との関係

P01は最新仕様のモデル・入力項目表への整理、P02は保存・API・画面契約、P03は実マスターと過去ログによる復旧検証、P04は現状の作業状態・ビルド・テストの確認である。その後にC01〜C65の実装コミット候補が続く。今回の依頼を全工程の実行承認とは扱わない。

全体ではController→UseCase→Repository→SQLxとRust-WASMを維持し、新旧モデルを段階的に切り替える。BCは許容され、旧DBのデータ移行は不要。再投入はマスター1行につき商品情報とボトル1本、その後の過去ログ再生を目指す。順序が同じだけでは二重適用防止を保証できず、実データからの復旧可能性はP03で検証する。

SNS共有、フォーク、HoneyLot、メモのブログ化、全Entityのゴミ箱・復元画面は今回の必須対象ではない。

## P01の成功条件

全Entityの所属、各入力の必須／任意、評価の両端・中立点・未評価、日時・量などの制約、商品検索の候補表示を具体的な表として確認できること。名前だけ登録・同一秒複数観察・観察論理削除を明記し、未確定事項を解消する。
